Resumen ejecutivo

Se implementó la base de datos operativa de QuickTrack en un clúster de MongoDB Atlas y se integró con una API REST en Python (FastAPI + PyMongo). Los cinco conjuntos de datos del caso (500 documentos) se cargaron con un proceso ETL idempotente que además normaliza la referencia entre órdenes y clientes. Sobre esa base se desarrollaron consultas con filtros, proyecciones, agregaciones y ordenamientos; su eficiencia se midió con explain(), volumen de datos y latencia. También se validó el ciclo CRUD completo desde scripts y desde la API.

Las pruebas confirman lectura y escritura en tiempo real y respuestas de error controladas (400, 404, 422 y 500). El análisis detectó además dos puntos accionables: inconsistencias en los datos de origen (82 de 100 órdenes tienen un estado distinto al de su seguimiento) y una mejora de rendimiento en la API. Ambos se documentan con su solución propuesta.

Objetivos del proyecto

Transversal

QuickTrack es una empresa de logística que ofrece entregas express a nivel nacional. Su sistema registra en una base de datos NoSQL las órdenes de entrega, el seguimiento de cada paquete, las rutas utilizadas y las valoraciones de los clientes. La gerencia necesita esa información disponible y consultable para optimizar rutas, identificar zonas críticas, medir la satisfacción del cliente y entender qué afecta el cumplimiento de plazos.

Objetivo general

Implementar y validar una base de datos NoSQL documental en MongoDB Atlas para los datos operativos de QuickTrack, integrada con una API REST en Python que permita consultar y modificar la información en tiempo real, con validación de entradas, control de errores y trazabilidad.

2.1Tecnología seleccionada y justificación

La pauta propone Azure Cosmos DB (APIs Core SQL, Gremlin o Table) u otras tecnologías equivalentes, y recomienda MongoDB Atlas por su disponibilidad gratuita y su conexión externa. Se eligió MongoDB Atlas, cuyo modelo documental es el equivalente directo de la API Core (SQL) de Cosmos DB.

Decisiones de modelado

  • Referencias entre entidades con ciclo de vida propio (clientes, rutas, órdenes): así no se duplican datos que cambian por separado.
  • Embebido para el historial de seguimiento: siempre se lee junto con su orden, crece acotado (de 2 a 4 eventos) y se actualiza de forma atómica con $push.
  • Relación 1:1 orden–seguimiento garantizada por el índice único orden_id_1.

2.6Problemas encontrados y resueltos

ProblemaCausaSolución
Los archivos de datos usan dos formatos JSON distintos.clientes.json es un arreglo; los otros cuatro son NDJSON (un documento por línea), y json.load() falla con NDJSON.Dos cargadores: cargar_coleccion_array() y cargar_coleccion_lineas().
El cruce órdenes–clientes devolvía 0 coincidencias.ordenes.cliente_id es texto ("cli_73") y clientes._id es entero (73).Normalización en el ETL: nuevo campo cliente_num_id. Resultado: 100 de 100 órdenes se unen a su cliente (§5.3).
Cargar dos veces duplicaba los datos.insert_many() agrega documentos sin revisar si ya existen.drop() antes de insertar: la carga es idempotente.
Credenciales escritas en el código.La URI incluye usuario y contraseña.Archivo .env + python-dotenv; si falta MONGO_URI, se lanza un ValueError explícito.
Las dependencias fijadas no se instalaron en Python 3.14.El proyecto se desarrolló en Python 3.13. requirements.txt fija pydantic 2.6.4 y pandas 2.2.1, que no publican paquetes precompilados para Python 3.14.Se instalaron versiones compatibles (FastAPI 0.162, Pydantic 2.14, Pandas 3.0). #Requerimiento de negocioOperadores y estructura
C1¿Cuáles son las órdenes entregadas de mayor valor (más de $100.000)?find() con filtro compuesto (igualdad + $gt), proyección de 5 campos, sort(total, -1) y limit(5)
C2¿Cuántas órdenes y cuánto monto hay por zona y medio de pago?Agregación: $lookup (rutas) → $unwind → $group con $sum/$avg → $project con $round → $sort
C3¿Qué órdenes recibieron valoraciones críticas (≤ 2) y en qué estado están?Agregación: $match con $lte → $lookup (órdenes) → $unwind → $project → $sort

4.3Consultas complementarias: zonas críticas y satisfacción

C4 y C5 responden directamente dos preguntas del caso: ¿dónde está la insatisfacción? y ¿qué zonas cumplen peor?. Ambas combinan tres colecciones con $lookup y calculan indicadores con $cond.

# C4 — satisfacción por zona (valoraciones → órdenes → rutas)
db.valoraciones.aggregate([
  {"$lookup": {"from": "ordenes_entrega", "localField": "orden_id", "foreignField": "_id", "as": "o"}},
  {"$unwind": "$o"},
  {"$lookup": {"from": "rutas", "localField": "o.ruta_id", "foreignField": "_id", "as": "r"}},
  {"$unwind": "$r"},
  {"$group": {"_id": "$r.zona", "valoraciones": {"$sum": 1}, "puntaje_prom": {"$avg": "$puntaje"},
              "criticas": {"$sum": {"$cond": [{"$lte": ["$puntaje", 2]}, 1, 0]}}}},
  {"$sort": {"puntaje_prom": 1}}])
# C5 — cumplimiento por zona: canceladas, entregadas y abiertas
db.ordenes_entrega.aggregate([
  {"$lookup": {"from": "rutas", "localField": "ruta_id", "foreignField": "_id", "as": "r"}},
  {"$unwind": "$r"},
  {"$group": {"_id": "$r.zona", "ordenes": {"$sum": 1},

Hallazgo: Centro es la zona crítica

Centro tiene la mayor tasa de cancelación (47,1 %), el peor puntaje promedio (2,71 de 5) y la mayor distancia promedio de sus rutas (1.468 km). Oriente es el caso opuesto en cancelación (7,7 %), pero acumula la mayor cantidad de órdenes abiertas (17 de 26). En total, 50 de las 100 órdenes siguen en preparación o en tránsito, aunque sus fechas de envío son de 2022 a 2024.

Limitación de los datos para medir plazos

Las 33 órdenes cuyo historial llega a «Entregado» demoran siempre exactamente 6 días (un evento cada 2 días), así que los datos no permiten medir retrasos reales. Además, el conjunto no incluye campos que el caso menciona: fecha de entrega, motivo de retraso, tiempo estimado, tipo de transporte y clima. Se recomienda incorporarlos para construir indicadores de cumplimiento de plazos.

Riesgo de atomicidad detectado

Crear, actualizar y borrar una orden escribe en 2 o 3 colecciones con llamadas separadas. Si una falla a mitad de camino (por ejemplo, el insert_one del seguimiento), queda una orden sin seguimiento. MongoDB permite transacciones multidocumento en replica sets: with client.start_session() as s: s.with_transaction(...). Así, las escrituras se confirman todas o ninguna.

Las correcciones propuestas no se ejecutaron sobre la base para conservar intacto el conjunto de datos oficial de la evaluación.

Conclusiones y próximos pasos

Conclusiones

  • Base funcional y bien configurada. MongoDB Atlas quedó operativo en un replica set de 3 nodos en São Paulo, con credenciales fuera del código, consistencia equivalente a Session y conectividad verificada con 4 herramientas.
  • Datos cargados y verificados. Las 5 colecciones coinciden documento a documento con sus archivos. La normalización del ETL hizo posible el cruce órdenes–clientes, que antes daba 0 de 100.
  • Consultas que responden al negocio. Filtros, proyecciones, agregaciones de hasta tres colecciones y ordenamientos identifican a Centro como zona crítica: 47,1 % de cancelación y 2,71 de satisfacción.
  • Eficiencia medida, no supuesta. Los índices reducen entre 73 % y 79 % los documentos examinados, y la búsqueda del seguimiento de una orden examina solo 1 documento. El cuello de botella real está en la API (un cliente nuevo por request, unas 20 veces más lento), y su solución es directa.
  • CRUD e integración en tiempo real. 14 de 14 pruebas dieron el resultado esperado, y cada escritura por HTTP se observó de inmediato desde otro cliente.
  • Calidad de datos como hallazgo. El 82 % de las órdenes tiene un estado distinto al de su seguimiento. Esto requiere una sola fuente de verdad para el estado antes de usar estos datos en reportes de gestión.
